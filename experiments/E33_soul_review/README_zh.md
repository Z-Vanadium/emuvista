# E33｜自动回顾能否改善履约

E33 在 E30 网络中运行 12 对隔离居民，覆盖两张人格卡和三种文档情境，每种组合各两对。两组从同一条旧挂心开始，得到相同的三条新经历。新经历表明核对正式版可以直接依据文件，无需再找负责人确认。唯一分组变量是是否开启 Soul 的自动回顾。居民也可以在观察阶段自行查找记忆或调整计划，因此本实验测量自动回顾带来的额外影响。

每个居民只收到一条启动公告，包含正式版预计发布时间和只读访问方式。正式版发布前是共同的等候阶段，启动公告要求先结束首轮。此后实验方不再发送或回复消息。正式版在启动约 60 秒后发布，观察窗为 240 秒。Cloud 探针确认新版的散列后，实验世界插件向两组各发一条仅陈述文件已发布的状态事件。它没有要求居民采取行动。有回顾组在首轮正常结束并完成自动回顾后才处理发布事件。两组都可以选择查看、继续等待，或自行另设提醒。周期唤醒和 Claw 唤醒关闭。轨迹分别标记唯一的外部输入、世界发布事件，以及居民自行安排的提醒。

主要指标是收到发布事件后，是否实际下载散列和隐藏标记均匹配的正式版，并把两项核对字段持久保存。自行预约、实际投递及是否履行额外承诺另列。这样两组都有一次同样的观察机会，可以看回顾改变了什么行为。结果不用于证明居民更会自己醒来。分析按配对统计。12 对属于探索性样本。

需要 E30 测试网络、已构建的 Soul、有工具能力的实验模型和 Python 3.11+。E32 的试验脚本负责创建临时测试账户、隔离 DSH 和验证下载；复用它的模型与网络环境变量。E33 不修改 E32 的既有实验数据。

```bash
python3 run.py release
```

新协议的数据写入 .runtime/run-release。历史 .runtime/run-v1 使用了热身与公告两条消息，保留作历史对照，不纳入单条启动消息实验。使用其他运行标签可另起批次。
